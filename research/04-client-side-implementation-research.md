# Client-side implementation research (deep-research run 2)

## Summary
A fully client-side form filler can be built as an MV3 extension with two layers. A content-script layer reads the page and does simple fills. A chrome.debugger (CDP) layer sends trusted input and reaches cross-origin iframes. The current Nanobrowser follows this design. Its control layer is deterministic and uses only chrome.debugger, with Puppeteer for frame tracking. Element IDs are bound to exact elements, and each action first checks that the element is visible, stable, enabled and not covered. Approval gates cover submit, send, delete and upload, and payment, password and grant steps go back to the user. For React-style controlled inputs, call the native prototype value setter, then dispatch a bubbling input event. Where per-key events matter, use CDP Input.insertText or Input.dispatchKeyEvent instead. To cover iframes and shadow DOM, combine all_frames and match_origin_as_fallback content scripts, scripting.executeScript with frameIds, and chrome.dom.openOrClosedShadowRoot for closed roots. Cross-origin out-of-process iframes need CDP flat sessions: Target.setAutoAttach with flatten:true, called again at each nesting level. Lighter options also stay on the device. Page Agent is in-page JS that reads a text DOM without screenshots, and the Browser Use Python library drives local Chrome over CDP from a desktop companion. For self-healing saved steps, Similo's weighted multi-attribute similarity score is a solid published basis for element fingerprints.

## Findings
- **[medium]** Nanobrowser architecture: the current README describes one agent on top of a deterministic browser-control layer with no AI model in it. That layer talks to the page only through chrome.debugger and uses Puppeteer to track frames. Clicks and typing are real browser input, which comes out as isTrusted=true. Each visible element gets an ID bound to that exact element, so a stale ID fails instead of hitting a different element. Before acting, the layer checks that the element is visible, not moving, enabled and not covered.
  - sources: https://github.com/nanobrowser/nanobrowser
  - evidence: README lines 137-143, quoted word for word by the verifiers. The latest commit is dated 2026-10-24. The README is the project describing itself and was not checked against source code. It no longer mentions the older planner/navigator/validator design, so older descriptions of Nanobrowser conflict with it. The trusted-input conclusion is inferred from how CDP Input works; the README does not use the word trusted.

- **[medium]** Nanobrowser delivery and privacy: everything runs in the browser through a side panel (Alt+Shift+N). API keys stay in the browser and go only to their own provider. Local models work through Ollama (needs OLLAMA_ORIGINS), LM Studio (needs CORS turned on), and llama.cpp or vLLM through the OpenAI-compatible provider. The README says local models work best for simple, clear tasks. Page content still goes to a cloud LLM when the user picks one.
  - sources: https://github.com/nanobrowser/nanobrowser
  - evidence: Verified against the live README. The only source is the project's own documentation.

- **[medium]** Confirmation-gate pattern (Nanobrowser): in Ask mode, the default, submit, send, delete and upload need user approval. In both Ask and Auto modes, paying, entering a password or code, or granting access is handed back to the user. Per-site Allow, Ask or Block rules live in Settings → Permissions. These gates work only when the agent recognizes the sensitive action ('When it does notice one, your settings always apply').
  - sources: https://github.com/nanobrowser/nanobrowser
  - evidence: Verified against the README. Detection of sensitive actions is not guaranteed, so any gate design needs a deterministic backstop. Examples: intercept form submit, flag type=password fields, and match payment fields by autocomplete=cc-*.

- **[medium]** Page Agent (Alibaba) is in-page JavaScript that needs no extension, Python or headless browser. It reads pages as a text-based, indexed DOM derived from browser-use's buildDomTree, with no screenshots and no multimodal LLM. An optional Chrome extension adds multi-tab work. It is a good fit for site owners who embed the agent, or for injection by your own extension. It covers only the page that loads it, and it still needs an LLM, local or cloud.
  - sources: https://github.com/alibaba/page-agent
  - evidence: README fetched 2026-10-29, quoted word for word. The CDN demo is v1.12.4. The project's own README does not describe in detail how the text DOM is built.

- **[high]** Browser Use is an MIT-licensed Python library (Python >= 3.11), not a browser extension. It can control a local browser, a Browser Use Cloud browser, or an existing remote browser over CDP. Browser.from_system_chrome() reuses the user's Chrome profile, and Ollama can serve as the local model. This makes it the reference for the desktop companion / local-CDP delivery path. The cloud browser is opt-in.
  - sources: https://github.com/browser-use/browser-use
  - evidence: Verified against the README, PyPI and pyproject. Since Chrome 136, --remote-debugging-port does not work on the default user-data-dir, so in practice the user's own Chrome means a copied or separate profile. Profile sync copies cookies only.

- **[high]** Trusted input from an MV3 extension through chrome.debugger: the extension API exposes only some CDP domains. Input, DOM, DOMSnapshot, Accessibility, Runtime, Page, Target and Fetch are among them. Input.insertText (experimental) inserts text the way an IME would. It fires keypress/beforeinput/input events but no keydown/keyup; Puppeteer's Keyboard.sendCharacter uses it. Input.dispatchKeyEvent takes type keyDown, keyUp, rawKeyDown or char, plus an experimental 'commands' array of editing commands such as 'selectAll'. Puppeteer sends keyDown when the key has text and rawKeyDown for modifier and navigation keys. Use insertText for plain controlled inputs. Use full key sequences for masked inputs and comboboxes that listen for keydown.
  - sources: https://chromium.googlesource.com/devtools/devtools-frontend/+/main/node_modules/devtools-protocol/pdl/domains/Input.pdl, https://developer.chrome.com/docs/extensions/reference/api/debugger, https://raw.githubusercontent.com/puppeteer/puppeteer/main/packages/puppeteer-core/src/cdp/Input.ts
  - evidence: Sources are the CDP PDL, the Puppeteer source (`this.#client.send('Input.insertText', {text: char})` and `type: text ? 'keyDown' : 'rawKeyDown'`) and the official domain list. The target element must already be focused. Attaching the debugger shows the 'started debugging this browser' infobar and needs the debugger permission, which matters for Chrome Web Store review. Only some Target methods are allowed for extensions.

- **[high]** Filling React controlled inputs without a debugger: React puts an instance-level value setter on each input it manages (_valueTracker). A plain el.value = x also updates the tracker, so React sees no change and skips onChange. Fix: call Object.getOwnPropertyDescriptor(HTMLInputElement.prototype,'value').set.call(el, v), then dispatch new Event('input',{bubbles:true}). Use HTMLTextAreaElement.prototype for textarea, and HTMLSelectElement plus a 'change' event for select. This works from the ISOLATED world, because DOM events cross worlds. The MAIN world (content_scripts world:'MAIN', Chrome 111+, or executeScript world:'MAIN') is needed only to read framework internals such as __reactProps$, __reactFiber$ or _valueTracker. The host page can tamper with MAIN-world scripts.
  - sources: https://gh.r-mj.com/cdpdriver/zendriver/pull/243, https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts, https://developer.chrome.com/docs/extensions/reference/api/scripting
  - evidence: Verifiers checked this against React's inputValueTracking.js and facebook/react issues #10135 and #11488. The mechanism is the same from React 16 to 19. The zendriver PR is on an unusual mirror domain, but React's own source backs it. This fix does not cover custom comboboxes or keydown-driven masked inputs.

- **[high]** Reaching frames with content scripts: content_scripts all_frames defaults to false, which means top frame only. Set it to true to inject into child frames. Each frame is matched against the URL patterns on its own, so a cross-origin iframe needs host permission for its own origin. match_origin_as_fallback (default false, Chrome 119+) injects into about:, data:, blob: and filesystem: frames by matching the origin of the frame's creator. chrome.scripting.executeScript can target allFrames, frameIds or documentIds (Chrome 106+). allFrames cannot be combined with frameIds or documentIds.
  - sources: https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts, https://developer.chrome.com/docs/extensions/reference/api/scripting
  - evidence: Primary Chrome docs, quoted word for word. When match_origin_as_fallback is set, match paths must be wildcards.

- **[high]** Reaching cross-origin (out-of-process) iframes with CDP: since Chrome 125, chrome.debugger supports flat sessions. First add a listener for Target.attachedToTarget. Then send Target.setAutoAttach with flatten:true. Address each child as {...source, sessionId: params.sessionId} in sendCommand. Auto-attach is not recursive, so call setAutoAttach again on each intermediate frame (A→B→C).
  - sources: https://developer.chrome.com/docs/extensions/reference/api/debugger
  - evidence: Official chrome.debugger reference. Only out-of-process iframes become separate targets. Enterprise policy can block attach with the error 'Host access is restricted by policy'.

- **[high]** Closed shadow DOM: chrome.dom.openOrClosedShadowRoot(element) (Chrome 88+) returns the open or closed shadow root an element hosts, and null if there is none. A content script can therefore walk closed roots, which return null through element.shadowRoot. Firefox's equivalent is element.openOrClosedShadowRoot.
  - sources: https://developer.chrome.com/docs/extensions/reference/api/dom
  - evidence: Official docs. The API takes an HTMLElement, so it works only in content scripts, not in the service worker. It reaches only frames where the script is injected.

- **[medium]** Self-healing locators: Similo (Nass, Alégroth, Feldt, Leotta, Ricca, 2022) finds an element by a weighted similarity score across many locator attributes instead of one locator. VON-Similo (2023) extends it. This is a sound basis for multi-attribute fingerprints in saved steps: re-score the candidates when the stored locator fails, and repair only the broken step.
  - sources: https://arxiv.org/abs/2208.00677
  - evidence: The arXiv abstract confirms the mechanism. It is academic work tested on test-automation benchmarks, not a production library. The specific failure-rate numbers (72/598 vs 146/598) were refuted 0-3, so cite no numbers.

## Caveats
Most Nanobrowser, Page Agent and Browser Use claims rest on each project's own README, with no review of source code. They show what is documented, not what reliably works. Nanobrowser's README has been rewritten: it now describes one agent on a deterministic layer, not the older planner/navigator/validator design. Older sources and buildDomTree-era descriptions may therefore be outdated. The React _valueTracker claim cites a GitHub mirror domain, but React's own source confirms it. Input.insertText and dispatchKeyEvent 'commands' are experimental CDP features. chrome.debugger shows a visible infobar, needs a powerful permission and can be blocked by enterprise policy. Chrome 136+ restricts remote debugging on the default profile, which weakens the 'drive the user's own Chrome' desktop path. Several research areas got no surviving verified claims: specific widget libraries (react-select, MUI, AntD, Select2, flatpickr, imask), file upload through DataTransfer, contenteditable, Angular and Svelte specifics, how Bitwarden, 1Password, Chromium autofill and Simplify fill fields, MV3 service-worker lifetime and storage, side panel and offscreen documents, Web Store policy, Electron, Tauri and native messaging, WebMCP, on-device models (Prompt API, WebLLM, Transformers.js), encrypted vaults (WebCrypto, WebAuthn PRF), Healenium and Testim, and BrowserOS, AIPex, Claude in Chrome and the Playwright MCP extension. Treat those areas as unverified by this run.

## Open questions
- How do password managers and job-application autofill extensions (Bitwarden, 1Password, Simplify) handle custom comboboxes, date pickers and masked inputs in practice? Do they use synthetic DOM events, key sequences or CDP?
- Will the Chrome Web Store accept a general-purpose form filler that requests the debugger permission? How much do users mind the debugger infobar, and can most fills fall back to content scripts?
- How capable is Chrome's built-in Prompt API (Gemini Nano) for mapping field descriptors to profile data, compared with sending only field descriptors to a cloud LLM?
- How should a saved-step runner keep progress across MV3 service-worker termination (chrome.storage.session vs IndexedDB, and resuming in the middle of a step)?
